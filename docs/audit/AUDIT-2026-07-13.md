### M-01 · `.gitlab-ci.yml:14`
**Wymiar:** C · Bezpieczeństwo  ·  **Kategoria:** `secret-scan-coverage-gap`

**Problem.** The live GitLab secret-scan job runs `gitleaks detect --source .` on a GitLab CI checkout, which by default is a SHALLOW clone (no GIT_DEPTH:0 / variables block exists in the file), so gitleaks only scans the last handful of commits and misses secrets committed earlier in history.

**Dowód.** `L14: `- gitleaks detect --source . --no-banner --redact -v`  (no `variables:`/`GIT_DEPTH` anywhere in the 22-line file). Contrast: the sibling .github/workflows/gitleaks.yml deliberately sets `fetch-depth: 0   # full history so leaks in old commits are caught`.`

**Poprawka.** Add a full-clone directive so the only enforced secret gate scans all history, e.g. add at top level:
  variables:
    GIT_DEPTH: 0
(or `GIT_STRATEGY: clone` with depth 0) so `gitleaks detect` sees the complete commit history like the GitHub job intended.

## `eos-kernel` — jądro (hardening pamięci + łatki aarch64)

### K-01 · 🟠 WYSOKIE · `src/arch/aarch64/interrupt/exception.rs:206`
**Wymiar:** C·bezpieczeństwo  ·  **Kategoria:** `crypto-weak-entropy`

**Problem.** The emulated RNDR/RNDRRS handler (lines 206-288) silently feeds a low-entropy CPU-jitter PRNG (fully deterministic under QEMU TCG and weak on emulators/DVFS-quiescent cores) into randd, which seeds the system CSPRNG, so all downstream keys/nonces/ASLR become predictable while the instruction always reports success (NZCV cleared to 0).

**Dowód.** `let mut jitter: u64 = cntvct_el0() as u64; for round in 0..48u64 { let t0 = cntvct_el0(); ... } ... stack.store_reg(rt, z as usize); stack.iret.spsr_el1 &= !(0xF << 28);  // always signals RNG success even where CNTVCT deltas are constant (TCG)`

**Poprawka.** Do not present this as a working hardware TRNG for the sole CSPRNG seed: emit a loud one-time boot warning that RNG is emulated/degraded, gate it behind an explicit insecure/dev build flag, mix in additional persistent per-boot entropy, and ensure the userspace CSPRNG is seeded from multiple independent sources rather than trusting emulated RNDRRS; on hosts with no measurable jitter set the failure flag (PSTATE.C=1) so randd blocks instead of accepting deterministic output.

### K-02 · 🟡 SREDNIE · `src/context/memory.rs:3164`
**Wymiar:** C·bezpieczeństwo  ·  **Kategoria:** `aslr-entropy`

**Problem.** On any target that is not x86_64/aarch64 (e.g. riscv64, x86-32 — both real kernel targets), the ASLR PRNG has zero per-boot entropy: the fallback aslr_cycle_counter() returns exactly the constant K=0x9E3779B97F4A7C15 on the first call (ASLR_STATE starts at 0), so the seed `s = counter ^ K` cancels to 0 and the whole splitmix64 sequence is identical on every boot, making mmap addresses fully predictable and defeating the ASLR feature on those arches.

**Dowód.** `let mut s = ASLR_STATE.load(Ordering::Relaxed); if s == 0 { s = aslr_cycle_counter() ^ 0x9E3779B97F4A7C15; }  // fallback: aslr_cycle_counter()==0.wrapping_add(0x9E37..) == K, so s = K^K = 0`

**Poprawka.** On the fallback path derive the seed from a real per-boot entropy source (an arch cycle/perf counter such as riscv64 `rdcycle`, or entropy already gathered by the kernel RNG) and never let the seed collapse to 0 — e.g. seed with `rng_bytes() | 1` and assert it is non-zero before use.

**Wymiar:** C·bezpieczeństwo  ·  **Kategoria:** `entropy`

**Problem.** Removing the FEAT_RNG feature gate makes randd execute RNDRRS unconditionally and trust whatever it returns as a secure seed, so on cores without FEAT_RNG the kernel's emulated splitmix64-seeded-from-CNTPCT value is accepted (have_seeded=true) and the 'NOT SECURE' warning is suppressed, presenting a predictable, boot-counter-derived seed as if it were a hardware TRNG.

**Dowód.** `asm!("mrs {}, s3_3_c2_c4_1", out(reg) rand); // rndrrs ... failure |= rand == 0; ... have_seeded = !failure;  (comment: kernel emulates RNDR/RNDRRS via splitmix64 seeded from CNTPCT)`

**Poprawka.** Detect whether real FEAT_RNG is present (or whether the value is emulated) and keep emitting the 'NOT SECURE' warning / defer seeding to virtio-rngd when only the emulated source is available, rather than silently treating a CNTPCT-derived PRNG value as cryptographic entropy.

### K-10 · 🟡 SREDNIE · `drivers/pcid/src/main.rs:361`
**Wymiar:** A·jakość  ·  **Kategoria:** `acpi-parsing`

**Problem.** resolve_link_gsi locates the ACPI Extended Interrupt Descriptor by scanning for the first byte equal to 0x89 in the _CRS buffer instead of walking the resource-descriptor chain, so a 0x89 data byte occurring inside a preceding descriptor is misread as the tag and a garbage GSI is parsed, silently misrouting the device's INTx.

**Dowód.** `let pos = bytes.iter().position(|&b| b == 0x89)?; let g = bytes.get(pos + 5..pos + 9)?; Some(u32::from_le_bytes([g[0], g[1], g[2], g[3]]))`

**Poprawka.** Parse the _CRS resource descriptors sequentially (large-descriptor length field = bytes[1..3]) and only interpret a byte as the Extended Interrupt Descriptor tag when it is at a descriptor boundary, then read the GSI at the validated offset.

### K-11 · ⚪ NISKIE · `drivers/net/usbnetd/src/main.rs:208`
**Wymiar:** C·bezpieczeństwo  ·  **Kategoria:** `untrusted-frame-parsing`

**Problem.** The RX parser ignores the actual bytes transferred (poll_read's `_status` length is discarded) and bounds the RNDIS packet against `buf.len()`, always the fixed 2048, so a device can set data_off/data_len to pull stale bytes from a previous larger packet into the Ethernet frame handed to smoltcp; also `data_off + data_len` is unchecked usize addition that wraps on 32-bit (i686), bypassing the `<= buf.len()` guard and panicking the RX thread on the out-of-range slice.

**Dowód.** `let data_off = le32(&buf[8..12]) as usize + 8; let data_len = le32(&buf[12..16]) as usize; if data_len > 0 && data_off + data_len <= buf.len() { let frame = buf[data_off..data_off + data_len].to_vec();`

**Poprawka.** Capture the transferred length from poll_read's status and bound the parse against that (`&buf[..n]`), and use data_off.checked_add(data_len) compared to the actual length so a hostile offset/length can neither read stale data nor overflow.

### K-12 · ⚪ NISKIE · `drivers/net/usbnetd/src/main.rs:309`
**Wymiar:** C·bezpieczeństwo  ·  **Kategoria:** `untrusted-frame-parsing`

**Problem.** rndis_query_mac computes `info_off = le32(&resp[20..24]) as usize + 8` and checks `info_off + 6 > resp.len()` with unchecked usize addition; on 32-bit targets a device-supplied InformationBufferOffset near u32::MAX wraps, defeating the bounds check and panicking on the `resp[info_off..info_off+6]` slice.

**Dowód.** `let info_off = le32(&resp[20..24]) as usize + 8; if info_len < 6 || info_off + 6 > resp.len() { return Err(Error::new(EIO)); } mac.copy_from_slice(&resp[info_off..info_off + 6]);`

**Poprawka.** Use checked_add for info_off and the +6 end, returning EIO on overflow before slicing.

### K-13 · ⚪ NISKIE · `drivers/pcid/src/main.rs:339`
**Wymiar:** A·jakość  ·  **Kategoria:** `correctness`

**Problem.** read_acpi_prt_routing flattens every _PRT table into one Vec keyed only by (device, pin), discarding the PCI bus/segment each _PRT belongs to, so on a system with more than one PCI root bridge two devices sharing the same device number but different buses collide and INTx is routed to the wrong GIC SPI.

**Dowód.** `routing.push((device, *pin as u8, gsi)); ... find(|(d, p, _)| *d == device && *p == pin_idx)  // no bus/segment component`

**Poprawka.** Record the owning bus/segment for each _PRT (derive it from the enclosing PCIx device scope) and include pci_address.bus() in the lookup key so routing is disambiguated per root bridge.

### K-14 · ⚪ NISKIE · `drivers/pcid/src/main.rs:235`
**Wymiar:** C·bezpieczeństwo  ·  **Kategoria:** `irq-routing`

**Problem.** gsi.saturating_sub(32) silently maps any GSI below 32 (the GIC SGI/PPI range) to SPI 0 instead of flagging it, so a malformed _PRT/_CRS producing GSI<32 routes the device to an unrelated interrupt line.

**Dowód.** `let gic_irq = gsi.saturating_sub(32); // GIC SPI index = GSI - 32`

**Poprawka.** Treat gsi < 32 as an error (log and return None from the routing match) rather than saturating to SPI 0.

## `eos-userutils` — login/OOBE (auth)

### R-01 · 🟡 SREDNIE · `src/bin/login.rs:141`
**Wymiar:** C·bezpieczeństwo  ·  **Kategoria:** `fail-open-auth-gate`

**Problem.** The re-check that is the ONLY thing enforcing R-602 fails open: if AllUsers::authenticator(...) returns Err or get_by_name returns None, the chained Option collapses to None and .unwrap_or(false) sets still=false, so the loop breaks and login proceeds to spawn_shell while the account is still on its default/blank credential.

**Dowód.** `let still = AllUsers::authenticator(Config::default()).ok().and_then(|users| users.get_by_name(uname).map(|u| still_default(u))).unwrap_or(false); if !still { ... break; }`

**Poprawka.** Fail closed: on any error keep looping. Replace .unwrap_or(false) with .unwrap_or(true) (treat unknown state as still-default), or restructure so that only an explicit, successful load that proves still_default(u)==false may break the loop; e.g. `match AllUsers::authenticator(...) { Ok(users) => match users.get_by_name(uname) { Some(u) if !still_default(u) => break, _ => continue }, Err(_) => continue }`.

### R-02 · ⚪ NISKIE · `src/bin/login.rs:137`
**Wymiar:** C·bezpieczeństwo  ·  **Kategoria:** `untrusted-binary-resolution`

**Problem.** login runs as root and launches the password tool by bare name via Command::new("passwd"), which is resolved through PATH; a PATH entry or writable directory ahead of the real passwd yields root code execution and lets a planted 'passwd' return 0 without touching the shadow (the re-check would then loop, but the planted binary already ran as root).

**Dowód.** `let _ = std::process::Command::new("passwd").arg(uname).status();`

**Poprawka.** Invoke the tool by its absolute, trusted path, e.g. std::process::Command::new("/usr/bin/passwd").arg(uname).status(); (adjust to the image's real passwd location, and clear/override PATH via .env_clear()/.env("PATH", "/usr/bin") for the child).

## `eos-orbutils` — desktop + orblogin + eos-settings

### R-03 · 🟡 SREDNIE · `launcher/src/main.rs:419`
**Wymiar:** A·jakość  ·  **Kategoria:** `pipe-handshake-robustness`

**Problem.** After the DESKTOP-READY handshake the bar keeps the desktop child's stdout pipe open but never reads from it again, so post-startup output from desktop accumulates in the fixed-size pipe buffer with no drain and can eventually block desktop's writes.

**Dowód.** `_desktop_stdout = Some(reader.into_inner()); // pipe kept open but never read after READY; desktop.rs warn!/error! on every failed launch fills the ~64KB buffer, then desktop blocks in write and the icon layer freezes.`

**Poprawka.** After consuming the READY line, drain the pipe for the session in a background thread (thread::spawn(move || { let mut s=String::new(); while reader.read_line(&mut s).map(|n|n>0).unwrap_or(false){ s.clear(); } });) instead of storing an unread into_inner() handle.

### R-04 · ⚪ NISKIE · `launcher/src/desktop.rs:239`
**Wymiar:** A·jakość  ·  **Kategoria:** `startup-panic`

**Problem.** The desktop and background helper binaries use .expect()/.unwrap() on display-size, window-creation, font-lookup and display-rect calls, so a transient failure panics the helper (crashing the icon/wallpaper layer) instead of degrading gracefully; the bar itself survives.

**Dowód.** `let (display_w, display_h) = orbclient::get_display_size().expect("desktop: failed to get display size"); (also desktop.rs:271 Window::new_flags, :277 Font::find; background/main.rs:828 get_display_rects; and Window::new_flags().unwrap() in the display loop)`

**Poprawka.** Replace these startup .expect()/.unwrap() calls with error!-and-return handling so a recoverable startup failure leaves the rest of the DE running.
